# Прототип интерактивного Dashboard реального времени

## 📌 Обзор задачи

Необходимо разработать Single Page Application (SPA) на React для отслеживания портфеля финансовых активов. Приложение должно отображать интерактивную таблицу акций и график стоимости в реальном времени. Данные поступают по WebSocket и через REST API.

Главный акцент задания — **архитектурное проектирование (System Design)**, **оптимизация производительности** при высокой частоте обновлений данных и **качество тестового покрытия**.

**Язык интерфейса:** русский. Все тексты, форматирование дат, времени и чисел — в российском формате.

---

## 🛠️ Технологический стек и требования к окружению

- **Фреймворк:** React 18+ (TS)
- **Архитектурная методология:** Feature-Sliced Design (FSD)
- **Управление состоянием:** Zustand
- **Тестирование:** Vitest + React Testing Library (для unit/integration), Playwright (для E2E)
- **Сборщик:** Vite
- **Стилизация:** Tailwind CSS

---

## 🎯 Функциональные требования

### 1. Страница дашборда (Dashboard Page)

- **Информационная панель:** Отображает общую стоимость портфеля, доступный баланс пользователя в USD и процент изменения за день.
- **Сетка виджетов:** Адаптивная сетка, содержащая виджет таблицы акций и виджет интерактивного графика.

### 2. Виртуализированная таблица акций (Stock Table Widget)

- Должна поддерживать стабильный рендеринг **10 000+ элементов** без задержек интерфейса. Обязательна реализация виртуального скролла (Virtual Scroll) — собственного или с использованием `react-window` / `react-virtuoso` / `@tanstack/react-virtual`.
- Колонки: Тикер, Название, Текущая цена (обновляется по WS), Изменение за 24ч (%), Количество в портфеле, Действие (кнопка покупки/продажи).
- Реализовать локальную фильтрацию по секторам рынка и текстовый поиск по тикеру/названию. Фильтрация не должна сбрасывать WebSocket-подписки. NOTE: не совсем понятно, почему фильтрация и поиск должны быть локальными. Ведь данные поступают частями с бекенда. Фронтенд не может их локально фильтровать, потому что он не имеет всех данных. Он может отфильтровать только то, что знает или имеет.

### 3. График стоимости актива (Stock Chart Widget)

- При клике на строку в таблице график переключается на выбранную акцию.
- График должен отображать исторические данные (полученные по REST API) с возможностью переключения таймфреймов (1D, 1W, 1M, 1Y).
- На график в реальном времени должны дорисовываться новые точки, приходящие из WebSocket-соединения.

### 4. Модуль управления портфелем (Portfolio Management Feature)

- При клике на кнопку «Купить»/«Продать» открывается модальное окно или встроенная форма.
- Пользователь вводит количество акций. Система автоматически рассчитывает `Total Cost` на основе текущей рыночной цены.
- Кнопка подтверждения блокируется, если у пользователя недостаточно баланса или введено некорректное число.
- После успешной симуляции транзакции баланс пользователя и количество акций в таблице мгновенно обновляются.

## ⚡ Требования к производительности и оптимизации (Критично)

- **Профилирование рендеров:** Обновление цены одной конкретной акции по WebSocket **не должно** вызывать рендеринг всей таблицы, соседних строк или графика (если выбран другой актив).
- **Throttling/Debouncing:** Частота обновлений с WebSocket может достигать 50 мс. Примените батчинг (batching) обновлений состояния или дросселирование (throttling), чтобы интерфейс оставался отзывчивым (60 FPS).
- **Утечки памяти:** Убедитесь, что при переключении графиков или размонтировании компонентов все WebSocket-подписки и таймеры корректно уничтожаются.

## 🧪 Требования к тестированию

### 1. Unit и Интеграционные тесты (Vitest + RTL)

- Покрытие бизнес-логики (хуки, стейт-менеджеры, селекторы, утилиты форматирования) должно составлять **не менее 85%**.
- Напишите тест на кастомный хук подписки на WebSocket с изоляцией сетевого слоя (mocking WS).
- Протестируйте форму покупки акции: валидация лимитов баланса и вызов обработчика транзакции с правильным контрактом данных.

### 2. End-to-End тесты (Playwright)

- Настройте паттерн **Page Object Model (POM)** для страницы дашборда.
- Напишите один сквозной пользовательский сценарий:
  1. Пользователь заходит на дашборд.
  2. Выбирает акцию в таблице.
  3. Открывает форму покупки, вводит валидное количество и совершает покупку.
  4. Тест проверяет, что баланс уменьшился, а количество акций в портфеле увеличилось на заданную величину.
- Все HTTP-запросы и WebSocket-данные в E2E-тесте должны быть изолированы (mocked) средствами Playwright (`page.route`).

## 🧱 Требования к оформлению и архитектуре

- Соблюдение строгой структуры **FSD** (`shared`, `entities`, `features`, `widgets`, `pages`). Проверьте отсутствие циклических зависимостей и нарушений cross-importing.
- Строгая типизация в TypeScript. Избегайте использования `any` и `as unknown as...`.
- Наличие базового CI/CD воркфлоу (`.github/workflows/ci.yml` или GitLab CI), который автоматически запускает линтинг (`eslint`), сборку проекта (`npm run build`) и тесты (`npm run test:run`) при пуше в репозиторий.
